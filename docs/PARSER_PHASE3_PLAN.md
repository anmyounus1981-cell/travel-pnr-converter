# Phase 3: validate Amadeus and safely switch the live converter

The synthetic Amadeus fixtures in `tests/fixtures/amadeus.ts` cover one passenger/one flight, three passengers/four flights, and two names on a single line with a wrapped flight, ARNK and a non-confirmed `HL2` segment. The handwritten oracle checks names, routes, RBD, raw status, original element numbers and physical line ranges. They contain no real PNRs. Amadeus publishes [travel agency training resources](https://amadeus.com/en/training/overview), but these invented displays have not been checked against a real cryptic Amadeus PNR or its training environment. They cannot establish universal Amadeus compatibility.

1. **Validate format with independently sourced, redacted Amadeus displays.** Cover grouped surname entries, infant/child association, multiple dated arrival lines, schedule changes, non-confirmed statuses, mixed flight/SSR/AP elements, page wrapping and NDC records. Compare every expected field and SourceSpan against the unflattened original. Keep synthetic fixtures marked as such.
2. **Add a strict parser-to-conversion adapter, separate from the grammars.** Replace only the `parsePnr` implementation in `lib/converter.ts` after review. Do not run the legacy global regex in parallel as an invisible fallback. Preserve duplicate passenger names and numbered segments. If `ParseResult` has any `blocking` diagnostic, reject saving and expose the affected original lines; a `review` issue must remain visible and require explicit agent confirmation.
3. **Resolve date/time storage before constructing `Flight.departure_at` and `arrival_at`.** `LocalFlightTime.date` currently contains a yearless GDS code, `arrival.date` is missing and the Supabase flight columns use `timestamptz`. A date created by guessing the current year or interpreted as UTC would be misleading. Add confirmed local date/year fields and verified time-zone metadata (via a new migration), or require the agent to enter dates and zone evidence before the adapter can serialize the existing columns. Treat `#` and explicit arrival date markers as evidence, not guaranteed year confirmation.
4. **Switch both callers together:** `app/Converter.tsx` function `parse()` and the automatic parse branch in `app/api/conversions/route.ts` currently call `parsePnr`. Make the server reparse raw text or validate a submitted structured result; never trust the client's edited array as proof that parsing passed. Keep invite-only authentication and per-owner RLS unchanged.
5. **Expose diagnostics and source evidence in the converter review UI.** Show detected GDS/confidence, passenger and segment counts, raw status, RBD and line excerpts. Prevent `save()` for blocking issues or unverified mandatory fields. Do not silently label an unverified passenger as adult or an RBD as Economy/Business. Preserve manual corrections with the original source evidence.
6. **Update exports and group layout.** `formatQuote` in `lib/converter.ts` and `generatePdf` in `lib/pdf/generator.ts` currently consume legacy `Conversion`; feed them only the reviewed canonical records. Paginate PDFs for 50–100+ passengers and segments and compare WhatsApp/PDF counts, routes and statuses to the saved conversion. Do not include a waitlisted `HL` flight as a confirmed booking.
7. **Release in controlled stages.** Run golden, malformed-input, large-payload, PDF-pagination, auth/RLS and tenant-isolation checks. Compare old and new outputs on dummy inputs, but use the original PNR as the oracle when they disagree. Deploy behind a server-controlled feature flag only after real Amadeus formats and date storage are verified, then monitor diagnostic rates before retiring the legacy implementation.

This milestone implements the isolated Amadeus grammar and synthetic assertions. It does **not** make any change to the live Converter, API, database or exports.
